## P0 — data loss / wrong money / crash / security

### P0-1 — Anon RLS share policies dump all invoices & receipts (security)
- `supabase/migrations/20240101000000_initial_poultry_schema.sql:563-564`:
  `CREATE POLICY "Public invoice view via share token" ON invoices FOR SELECT
  USING (share_token IS NOT NULL)` (same for receipts). The v2 migration
  `20261010000001_role_based_rls.sql` explicitly preserves them
  ("public share_token SELECT policy from v1 is preserved").
- The policy does NOT check that the caller knows the token — it is true for
  every row (tokens are default-generated on all rows). Any anonymous client
  with the publishable key (shipped in the JS bundle) can `SELECT *` from
  `invoices`/`receipts` with no filter: full sales history, amounts, dates,
  customer UUIDs, balances.
- Repro (needs live probe to confirm end-to-end): anon REST
  `GET /rest/v1/invoices?select=*` with only the anon key.
- Fix: bind the anon policy to the token actually presented (dedicated
  security-definer RPC / view that takes the token), or drop the permissive
  policy and serve public invoices through an RPC.

### P0-2 — Accounting Balance Sheet is entirely fabricated seed numbers
- `src/components/accounting/AccountingView.tsx`, Balance Sheet tab: every figure
  is a literal — Cash in Hand 840,000; Bank 1,450,000; Wallets 205,000; Customer
  Udhaar 650,000; Farm Bird Stock 920,000; Total Assets 4,065,000; Supplier
  Payables 490,000; Advances 11,600; Owner Capital 2,500,000; Retained Earnings
  1,063,400. Both sides always "balance" at 4,065,000 because the numbers were
  chosen to. No figure reads `accounts`, `parties`, or `inventory`.
- Repro: Accounting → Balance Sheet tab on any login. These are the 2024 demo-seed
  values, shown as the live business position.
- Related (P1): the P&L tab shows hardcoded "Vehicle Fuel & Maintenance −65,000"
  and "Salaries & Admin Expense −95,000" lines that are NOT subtracted from the
  displayed Net Profit, so the statement does not add up.

### P0-3 — Dashboard "Today" KPIs read dayClosing — FIXED IN TREE, NOT LIVE
- Original finding (this evening): `DashboardView.tsx` computed
  `todaySalesAmount = dayClosing.totalSalesAmount ?? 0`,
  `todayCollections = dayClosing.totalCollections ?? 0`, and charts/Reports table
  computed from synced `liveInvoices` — which is why the table showed data while
  the KPI cards showed 0. `dayClosing` is a local-only accumulator, mutated by
  `App.tsx` invoice/receipt/void handlers (`handleSaveInvoice` ~L559-564,
  `reverseInvoiceForVoid` ~L647-652, receipt handlers ~L797-857) and only written
  to the server on explicit day-close (`handleUpdateDayClosing`, App.tsx:1221) or
  Quick Setup (App.tsx:1351). `fetchDayClosing` (`db.ts:759`) returns the LATEST
  row by `closing_date` with no date check, and `reconcileState`
  (`remote.ts:221`) does `dayClosing: remote.dayClosing ?? prev.dayClosing` —
  server wins unconditionally. Repro: create a sale on laptop B; on laptop A the
  Reports table shows the invoice but "Today's Sales" = 0 all day.
- **Current status: fixed in the working tree** (`DashboardView.tsx` ~L120–150
  derives Today KPIs from `liveInvoices`/`receipts` filtered by
  `invoiceDate === todayStr`, with a comment explaining the defect).
  **Not in the live bundle `BY-ALen2`** — verify the new bundle hash after the
  next push. Do not re-report as an open code defect; the remaining Dashboard
  defects are P1-1…P1-5 below.

### P0-4 — Cash & bank KPI is local-only: `chart_of_accounts` is never written to the server
- No `persist(..., 'chart_of_accounts', ...)` call exists anywhere (only the
  `TABLE_STATE_KEY` mapping in `src/lib/remote.ts:71`). `handleAddGeneralEntry`
  (App.tsx) comments "Derived account/party/ledger adjustments stay local-only
  in v1". `fetchAccounts` reads the server table; the only server rows would
  come from `seed_demo.sql` (13 demo rows) — real balances are never synced.
- Result: any fresh device / fresh login shows Cash & Bank = 0 (screenshot:
  Rs 0) while a laptop with old localStorage shows stale seed/local balances.
- Fix direction: sync account balances (upsert on journal/invoice/receipt
  effects) or derive cash/bank from the synced ledger.

### P0-5 — Stock KPI can be 0 on a fresh device: stock sync depends on local inventory existing first
- `liveBirdsWeight/Count` (`DashboardView`) sum `inventory` rows with
  `category === 'broiler'`. `persistInvoiceStock` (App.tsx:678) only persists
  when it FINDS the broiler row in local inventory — if local inventory is empty
  (fresh/blank device, or scrubbed — see P1-6), the upsert never happens and the
  server `products` row is never created/updated. `loadSavedState` scrubs the
  seed row `inv-item-1` on every load (see P1-6), so a device that has never
  successfully fetched `products` can never create the server row from sales
  alone.
- Server `products` RLS allows any authenticated SELECT (`products_select`),
  columns match `mapProduct` — so a 0 here most likely means the server row is
  missing/zero, not a mapping bug. Needs a live DB check to confirm which
  (walkthrough).
- Fix direction: ensure the BR-LIVE product row is created server-side on first
  sale even when local inventory is empty (fallback `products` upsert by code
  with the computed weight), and/or seed the row once.

## P1 — feature broken / wrong money / data loss on refresh

### Dashboard
- **P1-1 — Expense ratio shows `NaN%` when 7-day gross gain is 0.**
  `DashboardView.tsx`: `avgExpenseRatio = Math.round((total7DayExpenses /
  total7DayGrossGain) * 100)` — no zero guard. Repro: a week with expenses but
  no sales → the "Expense Ratio" pill reads `NaN%`.
- **P1-2 — 7-day profit trend uses TODAY's mandi rate for all 7 days.**
  `dailyProfitTrendData` computes each day's `grossGain` as
  `(saleRate − todayMandiRate) × kg / 40`. Historical profit is wrong whenever
  the rate moved. The Mandi-vs-Sale chart is worse: `salesTrendData.mandiRate`
  is `todayMandiRate` for today and `0` for the other 6 days, so the red mandi
  line sits at 0 for most of the week.
- **P1-3 — "Est. Profit Today" uses the ALL-TIME average sale rate.**
  `mandiMarginSpread = avgSaleRate(all invoices ever) − todayMandiRate`;
  `estimatedProfitToday = todaySalesKg × spread / 40`. Wrong whenever
  historical rates differ from today's. Also renders a hardcoded `+` sign, so a
  negative spread shows as `+-200`.
- **P1-4 — Top Debtors WhatsApp reminder sends fabricated totals.**
  `DashboardView.tsx` (Remind button): `totalDebit: c.currentBalance + 50000,
  totalCredit: 50000`. The customer receives a statement with an invented
  Rs 50,000 credit. (The Daily Sheet pending tab does this correctly with
  `totalDebit: balance, totalCredit: 0` — copy that.)
- **P1-5 — `dateRange` state is dead.** Declared
  (`useState<'today'|'week'|'month'>('today')`) and never read or set anywhere;
  there is no date-range control. Harmless but confusing.

### Inventory / stock
- **P1-6 — Seed scrub deletes the local BR-LIVE inventory row on every load.**
  `src/services/store.ts` `isSeedId` regex includes `inv-item-\d+`;
  `scrubSeedRows` drops `inv-item-1` (the BR-LIVE row) from saved localStorage
  on every `loadSavedState`. The row is only restored by the next server
  refresh. Between load and refresh, inventory is empty — POS stock display and
  `persistInvoiceStock` (which needs the local row) see nothing. The seed
  `inv-item-2/3/4` rows are dropped the same way (by design — they are demo),
  but `inv-item-1` is the LIVE stock row reused by real sales. Its id should
  have been migrated to a UUID, or the scrub should exempt the row with
  `code === 'BR-LIVE'`.
  Repro: fresh load with slow/flaky network → stock card 0 and POS shows no
  stock until refresh lands.
- **P1-7 — Quick Setup stock set is a no-op on refreshed devices (F5 not fully fixed).**
  `App.tsx handleQuickBusinessSetup` maps inventory with
  `inv.id === 'inv-item-1'` only. After any server refresh the broiler row's id
  is a server UUID (`mapProduct` uses the server id; `rowProduct` upserts by
  `code`), so no row matches — local stock is unchanged AND the persisted
  `freshInventory` is unchanged, so the server stock is not updated either.
  (The Nov 22 fix made the persist use fresh values, but the id match is still
  seed-only; `handleAddPurchase`/`persistInvoiceStock` correctly also match on
  `code === 'BR-LIVE'`.)
- **P1-8 — Mortality reason is captured and then discarded.**
  `InventoryView.tsx handleRecordMortality` reads the `reason` field but never
  saves it anywhere: no mortality record, no ledger row, no audit trail. Stock
  just drops. Add-stock modal prefills 500 birds / 1000 kg (same prefilled-
  default hazard).

### POS
- **P1-9 — No stock-availability check; overselling is silent.**
  `POSView` receives no `inventory` prop at all. A sale can exceed live stock;
  `applyInvoiceToState` clamps the local row at 0 and `persistInvoiceStock`
  clamps the server row at 0, so the excess simply vanishes — stock goes to 0
  and the sale still posts in full.
- **P1-10 — Form rates/customer/vehicle initialise once from props, never resync.**
  `mandiRate`/`saleRate`/`selectedCustomerId`/`selectedVehicleId`/`weightKg`
  are `useState(todayMandiRate …)` / `useState(customers[0]?.id …)` with no
  effect. If `todayMandiRate` arrives after mount (refresh still running),
  the form keeps 0/stale rates; a 0 sale rate blocks saving with an alert, a
  stale rate posts a wrong-margin sale. Repro: open POS immediately after login
  on a slow connection.
- **P1-11 — Voice parser + quick chips use hardcoded 2024 demo rates/names.**
  `parseSpeechToInvoice` falls back to 12200/12000/13200/13000 and the sample
  chips name "Sami Khan / Haji Aslam / Malik Brothers". Voice input on a real
  customer sets a demo rate. (Same family as the old demo-rate scrub issue.)
- **P1-12 — Invoice `notes` never reach the server.**
  `POSView.createInvoiceObject` includes `notes`, but `rowInvoice`
  (`src/lib/db.ts:968`) never sends it (no `notes` key). Notes typed in POS are
  local-only and vanish on refresh / never appear on other devices.

### Receipts / ledger / accounting
- **P1-13 — Receipt modal ignores the preselected party after first mount.**
  `ReceiptModal.tsx` does `useState(preselectedPartyId || parties[0]?.id)` with
  no effect syncing the prop, and the modal stays mounted in `App.tsx`. Every
  "Collect" / "Make Payment to Supplier" button passes a party id that is
  silently ignored — the modal opens on whichever party was selected last (or
  `parties[0]`). Wrong-party receipt risk.
- **P1-14 — Supplier payments show as cash IN in the Roznamcha.**
  `AccountingView.tsx` puts every receipt into `cash_in`/`credit`. A standalone
  supplier payment (via ReceiptModal, partyType supplier) therefore appears as
  cash received, inflating the day's Jama. `handleSaveReceipt` itself gets the
  safe direction right (supplier cash deducts) — only the Roznamcha view is
  wrong. Also: JV rows add their amount to BOTH `totalJama` and `totalNaam`
  (debitAmount = creditAmount = amount), double-counting every JV in the grand
  totals; and `cashInToday`/`cashOutToday` filter journal rows by
  `accountTitle.includes('1010')`, which can never match (account titles carry
  names, not codes) — dead code.
- **P1-15 — Customer Ledger aging brackets are fabricated — and rendered.**
  `CustomerLedgerView.tsx:111-116` + rendered at L606-618: `current = balance ×
  0.4, 8–15d × 0.3, 16–30d × 0.18, 30+d × 0.12`. Presented as an aging analysis
  but never computed from entry dates. (Correction to the earlier partial audit:
  the Dashboard's `stockPieData`/`agingData` constants are dead code — defined
  but never rendered — downgraded to P2-1. The ledger aging IS rendered.)
- **P1-16 — JV party-balance logic uses the wrong account code.**
  `App.tsx handleAddGeneralEntry` treats account `1020` as the customer /
  receivables account (`isCustomerCredit = creditAccountCode === '1020'`), but
  `1020` is Meezan Bank (`store.ts:522`). A JV with a linked party moves that
  party's balance backwards (debit 1020 → party +amount). The JV modal's
  DEFAULT is debit 5030 / credit 1020, so a default JV with a party linked
  silently reduces that party's balance. Also the local account-balance
  adjustment treats every account as an asset (debit +, credit −, clamped at 0)
  — wrong direction for liability/equity/revenue accounts.
- **P1-17 — Day closing is server-wins with no date check.**
  `remote.ts reconcileState`: `dayClosing: remote.dayClosing ?? prev.dayClosing`.
  A stale server closing overwrites today's local accumulations on every
  refresh. Same shape for `todayMandiRate` (remote-wins can revert a locally
  set newer rate while its persist is still queued offline).

### Fleet
- **P1-21 — Trip stops / delivery progress are local-only and vanish on refresh.**
  `rowTrip` (`db.ts:1216`, comment in code): "App-only fields (plateNumber,

- **P1-22 — Trip numbers are length-based (F1 class, again).**

  `` `EMP-${100 + employees.length + 1}` `` → `employee_code` UNIQUE violation
  after a delete. Use the `nextDocNumber` max+1 helper like INV/REC/JV now do.

### HR

- **P1-24 — New-employee default CNIC is fake data saved as real.**
  `HRView.tsx`: `cnic: newEmpCnic.trim() || '35201-0000000-1'`. Also the

### Settings / backup / restore
- **P1-25 — Quick Setup wizard silently discards the shop name / owner / city.**
  The wizard collects shop Urdu/English name, owner name and city, but
  `App.handleQuickBusinessSetup` only applies mandi rate, cash, stock and a

  It also does NOT clear existing data despite "fresh shop setup / clean shop

  Wizard defaults themselves are stale/personal: owner "حاجی محمد اکرم",

- **P1-26 — Backup restore breaks references for seed/demo backups.**

- **P1-27 — "Reset to Demo Seed" sits one confirm away from live data.**
  Settings offers a prominent reset that replaces local state with demo seed
  (Sami Khan etc.). The seed rows never sync, so the next refresh restores
  server data — the button is confusing at best and a foot-gun at worst.

### Daily Sheet
- **P1-28 — Voided invoices' on-the-spot collections still count as recoveries.**

### Cross-cutting
- **P1-29 — "Today" is UTC everywhere (38 call sites, 15 files).**
  `new Date().toISOString().split('T')[0]` in POS invoice date, ReceiptModal,
  Expenses, Orders, Fleet, DailySheet, Accounting, ledger filters, dayClosing
